# Deployment

Production runs on cPanel hosting (`animecream.com`), not Docker/Kubernetes/a cloud provider — this file describes that real mechanism only.

## Two independent things get deployed

1. **`module-api`'s own application code** (this repo).
2. **The database schema** (`animecream-data`, `auth-data`, `finan-data` — three separate sibling repos, see `docs/specification-roadmap.md`'s multi-repo note).

They ship through similar-looking but separate pipelines, both under a `com/` folder of batch scripts + a gitignored `.env.deploy` file of deploy credentials (`keys/*.txt` symlinks, until 2026-07-19 — see auth-data's archived `docs/credential-migration-runbook.md`), synced to production via a Google Drive Desktop–mounted FTP folder.

## Deploying `module-api`'s code

```bash
npm run bup   # = npm run build && call com/db-sync-FTP-both.bat
```

Builds TypeScript to `dist/`, then FTP-syncs the built output up via `com/db-sync-FTP-both.bat` (the same sync mechanism the schema repos use, see below). This repo's own `.env` on the production server is edited directly (by SSH/FTP), not templated or regenerated by this script — see `docs/setup.md` for the real variable names.

### What actually happens (verified 2026-11-01, Bitácora deploy, change `20261031-bitacora-day0`)

- **Credentials:** `com/setter.bat` loads the gitignored `.env.deploy` (FTP user `info@animecream.com`, password, server, `LocalPath.txt=D:\Proyectos\module-api\dist`, `FTPFolder.txt=dist`, `Link_restart_node.txt`). Its master copy lives in the owner's Drive (`FTPSync\module-api\.env.deploy`) and `0.symbolics.bat` copies it in.
- **Server layout (FTP root of `info@`):** `dist/`, `node_modules` (symlink, managed by cPanel), `package.json`, `.env` (the production app config), `uploads/`, `public/`, `stderr.log`. The production `.env` sits **next to** `dist/`, not inside it.
- **Upload:** `synchronize remote` from local `dist\` to `/dist` — upload only, never deletes remote files. A fresh `tsc` touches every file's timestamp, so the whole `dist/` is re-uploaded (~1 minute).
- **Restart is manual and required.** The script opens `Link_restart_node.txt` in the browser **before** uploading — it is cPanel's *Setup Node.js App* page (`…/lveversion/nodejs-selector.html.tt#/applications/info.animecream.com`), not an endpoint that restarts anything. Node keeps serving the old code until someone clicks **Restart** there, **after** the upload has finished. Confirmed: `/health` `uptime` stayed at ~830 s after the upload and dropped to < 1 s only after the manual restart.
- **New environment variable?** Add it to the production `.env` (cPanel File Manager or FTP) **before** the restart. Example: `MYDATABASEBITACORA=animecre_bitacora`.
- **Running it from an agent:** invoke the `.bat` by absolute path with stdin redirected (see `docs/specification-roadmap.md` Phase 5b); the final `TIMEOUT` then fails with "Input redirection is not supported" and the exit code is 1 — harmless. Mask the FTP password in any captured output.

### Post-deploy check (read-only — no writes in production, playbook D.1)

```bash
curl -s https://info.animecream.com/health                                   # "status":"UP", uptime small = restarted
curl -s -o /dev/null -w '%{http_code}' https://info.animecream.com/api/bitacora/trash   # 401 = module mounted, auth gate on
curl -s https://info.animecream.com/api-docs/swagger-ui-init.js | grep -o '"/api/bitacora[^"]*"' | sort -u   # 7 paths
```

## Deploying the database schema

Each of the three sibling schema repos has its own `db-deploy-schema.bat` at its root, running a 4-step, confirmation-gated pipeline (build the incremental SQL → test locally → FTP-sync → apply to the live production database via SSH). **Full mechanics — exact scripts, the non-interactive-invocation quirks, the real success signal to trust, credential file naming — are documented in `docs/specification-roadmap.md` Phase 5b.** Don't duplicate that here; it was written from a real, verified production run and updating two copies would just let them drift.

Short version: `db-structure.sql` is bootstrap-only (destructive, only for a fresh database); `db-views-procs.sql` and `db-trigger.sql` are idempotent and re-run on every deploy; `sql/migrations/000N_*.sql` are incremental and never edited after being committed.

## Image file storage (cPanel symlink)

Series cover images are physically stored in the public web root and mirrored into the upload path via a symlink, so the app can keep saving to its normal `uploads/series/img/tarjeta` path while the files are actually served from a publicly-accessible folder:

- Real folder: `/home/animecre/public_html/webroot/img/tarjeta`
- Symlinked from: `/home/animecre/info.animecream.com/uploads/series/img/tarjeta`

```bash
ln -s /home/animecre/public_html/webroot/img/tarjeta /home/animecre/info.animecream.com/uploads/series/img/tarjeta
```

## What this file deliberately does not cover

Generic cloud/container deployment (AWS/GCP/Azure/Kubernetes/a from-scratch CI/CD pipeline, PM2, nginx load balancing) — none of that is how this project actually runs today. If the app is ever migrated to one of those, rewrite this file against the new real mechanism rather than resurrecting the old generic version of it.
